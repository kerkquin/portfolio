Trace the case, checks, and evidence

Problem

The same expected behavior can be implemented differently on iOS and Android. Those checks need to be reviewed before treating the platform results as equivalent.

Source test case

The flow header and candidate register identify a required-field case: the action button should remain disabled while the field is empty. The original master test-case export was not part of the inspected evidence chain.

Automation candidate

The register explicitly separates candidates ready now, candidates needing setup, and manual-only work. The selected case is marked ready for automation.

Implementation and assertions

The iOS flow directly checks that the button is disabled. The Android flow taps the button and checks that specified next screens do not appear. These are different assertions and are not presented as equivalent proof.

Evidence reviewed

  • Candidate classification and identifiable case intent in the flow header.
  • Separate iOS and Android Maestro flows with inspected assertions.
  • Saved Android failure, retry report, and matching completed assertion records.

A green flow is not enough if the assertions prove a different behavior from the original case.

DOCUMENTED PRACTICE / REQUIREMENTS

Acceptance-criteria review and change verification

A review process for identifying ambiguity, assigning clarification owners, and rechecking findings when the acceptance criteria change. I connect the review decisions to the cases that depend on them.

My role
Test design, requirements review, and verification
Deliverables
AC review findings, clarification records, BDD test cases, change-verification notes.
Approach and contribution

Problem

A requirement can look complete while leaving critical behavior undecided. Later edits can also invalidate a finding or break the link between a scenario and its tests.

My contribution

  • Review criteria and design material before generating test cases.
  • Assign clarification owners and distinguish blocking findings from advisory notes.
  • Revisit earlier findings when criteria change, preserving their identifiers and recording the decision.
  • Write BDD-style cases with traceability and visible execution dependencies.

When behavior is unclear, I ask for a decision before treating it as an expected result.

Documented practice. A specific redacted finding-to-change-to-result case is not included; no defect-prevention or productivity metric is claimed.

DOCUMENTED PRACTICE / MOBILE & RELEASE

iOS and Android design-to-build reviews

Platform comparisons that check the design against each build and distinguish defects from native behavior or an outdated reference. I combine the comparisons with release checks and fix-verification evidence.

My role
Hands-on testing, review, and defect verification
Deliverables
Platform comparison notes, risk-based release checklists, reproducibility records, fix-verification evidence.
Approach and contribution

Problem

A matching screen is only one part of quality. Platform conventions, existing user state, stale content, and failed connections can change the experience.

My contribution

  • Compare design to iOS, design to Android, and behavior across platforms.
  • Distinguish expected native behavior and stale design references from defects.
  • Plan checks that require an upgrade from the previous build rather than a fresh install.
  • Use network-failure scenarios and confirm expected behavior when re-verifying a fix.

I record what was checked on each platform and verify a fix against the expected behavior.

Documented practice. A result-verified release or comparison case is not included; results are not inferred from one platform to another.

Edit a display name

The example requirementA signed-in user can update their display name. Leading and trailing spaces are trimmed before validation. The saved name must contain 1 to 50 characters and remain visible after a page reload. An invalid name must not replace the saved value.

Character counting

How are emoji and combined Unicode characters counted?

The boundary can change across browser and server implementations.

Failed save

What message and retry behavior are expected when the save request fails?

The requirement defines validation failure but leaves network failure undecided.

Concurrent edits

What should happen when the same profile is edited in two sessions?

A later save may overwrite a value without the user realizing it.

These cases cover the defined behavior. I would settle the network-failure and Unicode questions before adding expectations for them.
