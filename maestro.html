Reviewed work / Maestro / MOBILE-01

What does a passing
mobile flow actually prove?

A required-field case shows why an assertion deserves as much attention as a green result, especially when iOS and Android use different checks.

My role: QA direction, candidate and script review, hands-on validationScript preparation: AI-assisted

From generated case to automation candidate

A candidate register separates cases ready for automation, cases needing setup, and manual-only work. The selected required-field case is marked ready; its flow header describes the intended behavior: the action button should remain disabled while the field is empty.

I led QA work, reviewed automation candidates and agent output, and performed hands-on validation. The original master test-case export was not part of the reviewed evidence chain; the case intent is supported by the register and flow header.

Two checks. Different conclusions.

PlatformInspected assertionWhat it checks
iOSAsserts the button is visible with enabled set to false.Directly checks the disabled state.
AndroidTaps the button, then checks that specified next screens do not appear.Checks navigation does not advance to those screens; does not directly prove the button is disabled.

The review question

Could this flow pass while the original expected behavior is still wrong? If so, the assertion needs attention before its result can support the full case.

Look at the direct state check

This reconstructed iOS-style flow illustrates the disabled-state assertion using a fictional application and accessibility identifier. Its setup assumes a dedicated demo app opens the form with the required field empty.

Reconstructed Maestro flow · fictional app and selector
# Fictional demo app starts on an empty required-field form.
appId: com.example.qademo
---
- launchApp:
    clearState: true
- assertVisible:
    id: "profile-name-input"
- assertVisible:
    text: "Next"
    enabled: false

AI-assisted reconstruction for this portfolio, not original client code or a fresh execution result. This is the direct state-check approach; it does not represent the Android navigation assertions. The app ID and selector are fictional.

What the evidence establishes

Android retry passed its navigation checks

The saved Android retry passes its navigation checks, but those checks do not directly verify that the button is disabled. The full disabled-button expected result remains unverified there.

An iOS assertion was inspected, but a matching iOS execution was not reviewed. No current-build or cross-platform pass is claimed.

The reviewed material includes the candidate classification, separate platform flows, an earlier Android failure, and the retry report with completed assertion records. This example demonstrates why platform results must be read alongside their actual checks.
