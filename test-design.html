QA demonstration / fictional scenario

A small feature.
A lot worth checking.

Editing a display name looks straightforward. The interesting work is deciding what must stay true when an edit is invalid, a save fails, or the requirement leaves something open.

Focus: test design and QA judgmentFormat: five-stage walkthrough

Created for this portfolio with fictional data and AI-assisted preparation, to illustrate my approach. This is a demonstration of proposed tests and expected checks; it contains no client execution results.

01 / Understand the behavior

What does “saved” mean?

The fictional requirement

Edit a display name

A signed-in user can update their display name. Leading and trailing spaces are trimmed before validation. The saved name must contain 1 to 50 characters and remain visible after a page reload. An invalid name must not replace the saved value.

The property I want to protect

A rejected edit must leave the previously saved name intact. Seeing a validation message alone would not prove that.

02 / Decide what matters first

Protect the data. Resolve the unknowns.

I would start with persistence and invalid edits because the user could otherwise see an apparently successful change or lose a valid name. Boundary checks then help locate errors in validation.

  • First checks

    Save a valid name and reload. Then attempt an invalid edit and confirm the original saved value remains. These checks cover the essential user journey and data integrity.

  • Boundaries

    Use 1, 50, and 51 ASCII characters, plus spaces only. ASCII makes the initial boundary expectations unambiguous while character-counting rules are being clarified.

  • Ask before testing

    How are emoji and combined Unicode characters counted? What feedback and retry behavior should follow a failed save? What happens when two sessions edit the same profile?

  • Scope decision

    Keep network failure, Unicode counting, and concurrent-edit expectations open until agreed. Record the uncertainty instead of inventing a pass condition.

03 / Turn the requirement into checks

Five cases with a clear purpose.

Each case starts with an existing saved name and a signed-in user. The result should be observable after reload, so the tests check persistence as well as immediate feedback.

04 / Select an automation candidate

Automate the rule you can explain.

TC-04 is a useful candidate because its input and expected result are explicit and repeatable. The assertion must check that the saved data survived the rejected edit, not just that a message appeared.

Fictional setup / agreed demo assumptions

The example assumes an isolated test profile, a signed-in Playwright fixture, a configured demo base URL, and an editable input that permits submitting 51 characters. It also assumes a Save changes button and the agreed validation message below. A product that prevents typing or submitting invalid input needs a different test path.

Reconstructed Playwright / TypeScript · illustrative test
import { test, expect } from '@playwright/test';

test('TC-04: invalid edit preserves the saved name',
  async ({ page }) => {
    // Demo baseURL and authentication are configured.
    await page.goto('/profile');
    const name = page.getByLabel('Display name', { exact: true });
    const save = page.getByRole('button', {
      name: 'Save changes', exact: true
    });

    // Establish a known saved value on an isolated test profile.
    await name.fill('Alex Morgan');
    await save.click();
    await expect(page.getByRole('status'))
      .toHaveText('Profile saved');
    await page.reload();
    await expect(name).toHaveValue('Alex Morgan');

    // Submit one character beyond the agreed ASCII limit.
    await name.fill('A'.repeat(51));
    await save.click();
    await expect(page.getByRole('alert'))
      .toHaveText('Use 1 to 50 characters.');

    // The rejected edit must not replace persisted data.
    await page.reload();
    await expect(name).toHaveValue('Alex Morgan');
  }
);

This complete test example was prepared with AI assistance for the fictional walkthrough. It has not been executed against a provided application. The real-work examples describe my QA direction, script review, and hands-on contribution separately.

What I would review in the draft

Does the setup establish known data? Do locators match the actual interface? Does the validation message come from an agreed requirement? Does the final assertion verify persistence? Can the test run without changing another tester’s data?

05 / Explain what the checks would establish

A useful result tells the whole story.

For TC-04, a pass would require both rejection of the invalid edit and preservation of the saved name after reload. These are expected checks for the demonstration, not recorded execution results.

Expected checks

Before calling the case passed

  • The known valid name is saved and survives reload.
  • The 51-character input is rejected with the agreed feedback.
  • The previously saved name still exists after the rejected edit and reload.

Evidence to retain

Build and environment, test data, relevant screenshots or trace, and actual assertion results. Investigate inconsistent reruns rather than reporting only the latest green result.
